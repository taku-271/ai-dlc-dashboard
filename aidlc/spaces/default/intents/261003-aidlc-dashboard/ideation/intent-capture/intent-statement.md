## 1. 問題定義（Problem Statement）

AI-DLC を Claude Code で運用する開発者は1人ですが、AIエージェントは複数の Intent を並行して進めます。
承認ゲートを通せるのは開発者だけなので、**「開発者の承認待ち」で作業が止まったまま気づかれない**状態が起きやすくなっています。

- 現状、開発者は Claude Code のセッション（ターミナル）を順に覗いて状況を確認しており、**ときどき承認待ちを見落としている**（Q1: B）。
- `/aidlc --status` は、いま選んでいる Intent の状況しか表示しない。全 Intent をまとめて見る手段がない。
- 今後は別々のリポジトリにある複数の AI-DLC プロジェクトを並行して進める予定で、見て回る範囲はさらに広がる（要件変更その2）。

解決したいのは「状況を把握するために見て回る手間」と「その結果起きる承認待ちの見落とし・滞留」です。

## 2. 対象ユーザー（Target Customer）

| 区分 | ユーザー | 抱えている困りごと | 得られる価値 |
|------|----------|-------------------|--------------|
| 主（現在） | AI-DLC を Claude Code で運用する個人開発者（本プロジェクトのオーナー本人） | 複数セッションを巡回しないと全体が分からず、ときどき承認待ちを見落とす | 開きっぱなしのブラウザタブ1つで、全プロジェクト・全 Intent の状況と承認待ち件数が分かる |
| 副（将来） | 同じく AI-DLC を使う他の開発者（OSS公開時の利用者） | 同上 | 同上。導入しやすさ（設定・ドキュメント）が価値の一部になる |

- 利用者の範囲は「自分用が主、将来OSSとして公開する可能性あり」（Q6: B）。社内・チーム配布は前提にしない。
- 利用スタイルは「作業中はサーバーを起動したまま、ブラウザのタブを常時開いておき、裏のタブのタイトルに出る件数で気づく」（Q3: A）。

## 3. 成功指標（Success Metrics）

ユーザーが選んだ指標は Q2 の B と C です。

| ID | 指標 | 判定方法 | 目標 | 状態 |
|----|------|----------|------|------|
| SM-1 | ダッシュボードを1回見るだけで、全 Intent の状況把握が完了する（Q2: C） | ダッシュボード上に「承認待ち」「修正中」「各 Intent の現在ステージ・進捗・最終更新日時」が出ていて、状況把握のためにセッションの巡回や `/aidlc --status` の実行が要らないこと。受け入れ時に実プロジェクトで `/aidlc --status` と照合し、食い違いが0件であること | 食い違い 0 件 | 確定 |
| SM-2 | 承認待ちの滞留時間（承認待ちになってから承認／差し戻しされるまで）の中央値が、導入前より短くなる（Q2: B） | 監査ログの「承認待ち開始」から「承認／差し戻し」までの時間の中央値を、導入前（ベースライン）と導入後で比べる | ベースラインを測ってから requirements-analysis で数値を決める | **前提付き（下記）** |

**SM-2 の前提と注意（仮説）:**
AI-DLC では、承認待ちの記録（状態ファイルの `[?]`）を省略できます。省略されたゲートは、承認または差し戻しの時点で「承認待ち開始」の記録が後から補完されます（監査ログに `Recovered: true` が付く）。
こうしたゲートは記録上の待ち時間がほぼ0になり、中央値を実態より短く見せてしまいます。
そのため、**補完された記録をどう扱うか（除外するか、別の方法で開始時刻を推定するか）と、ベースラインの取り方は feasibility で確定します**。それまで SM-2 は「仮説段階の指標」として扱います。

※ 「ダッシュボード表示が速い」（Q2: E）や「放置ゼロ件」（Q2: D）は、成功指標としては選ばれていません。ただし「ファイル変更から数秒以内に画面へ反映」は**機能要件**として残ります（具体的な秒数は requirements-analysis で決めます）。

## 4. なぜ今か（Initiative Trigger）

- **実害が出始めている:** すでに複数 Intent の並行運用で、ときどき承認待ちを見落としている（Q1: B）。予想ではなく、現に起きている問題です。
- **規模が広がる予定:** 今後は複数リポジトリでの並行運用に広がり、巡回して確認するやり方には限界がある（要件変更その2）。
- **既存の手段では足りない:** `/aidlc --status` は Intent ごとの確認手段で、横断した一覧の機能はない。

## 5. 初期スコープの見立て（Initial Scope Signal）

**スコープ: `mvp`**（ワークフロー開始時の設定と一致。変更不要と判断）

### MVPに含めるもの

1. **ブラウザで見るダッシュボード:** ローカルでサーバーを起動し、ブラウザで開く（Markdownファイル出力は廃止）。
2. **承認待ち一覧（最上部）:** `[?]` のステージを**全プロジェクト横断で1つの一覧**にまとめ、どのプロジェクト・Space・Intent のものかが分かるようにする。可能なら、承認待ちになった日時も出す。
3. **修正中一覧:** `[R]` のステージを出す。
4. **Intent 一覧:** 各 Intent の現在ステージ、進捗（完了数／スキップを除く総数）、最終更新日時を出す。
5. **表示の階層:** 「プロジェクト → Space → Intent → ステージ」。
6. **自動反映:** `aidlc/` 配下のファイル変更を検知し、画面をリロードせずに数秒以内で表示に反映する。
7. **タブタイトルの件数表示:** 承認待ちが1件以上あるとき、ブラウザのタブのタイトルに件数（全プロジェクトの合計）を出す（Q7: A）。
8. **監視対象は設定ファイルで指定:** ダッシュボード側の設定ファイルに、監視するプロジェクトを書く（Q8: A）。当初要件の「パス引数で指定、省略時はカレントディレクトリ」は、これに置き換える。
9. **複数件前提の作り:** MVPで実際に監視するのは1件でもよいが、データの持ち方と画面は複数プロジェクト前提で作る。1つのプロジェクトが読めない・壊れていても、他のプロジェクトの表示は続ける。

### MVPに含めないもの（後で検討）

| 項目 | 出典 | 扱い |
|------|------|------|
| 「回答待ち」（質問ファイルの未回答）や「承認待ちの可能性が高いもの」の検出 | Q5: D | MVP は `[?]` のみ。feasibility の調査結果を見てから追加するかを決める |
| ファビコンのバッジ、デスクトップ通知 | Q7: A | MVP はタブタイトルの件数のみ |
| ログイン時の自動起動・常駐 | Q3: A | MVP は手動で起動し、タブを開いておく運用 |
| ルール数の推移（学習ループの成果の可視化） | 当初要件 | MVP後に検討 |
| セッションコストの表示 | 当初要件 | MVP後に検討 |

### スコープ外

- 承認操作をダッシュボードから行うこと（承認は必ず Claude Code 上で行う）
- 外部への通知（Slack など）

## 6. 前提・制約（ユーザー指定）

以下はユーザーが要件として指定した制約です。具体的な実現方法は Inception 以降で設計します。

| ID | 制約 | 出典 |
|----|------|------|
| C-1 | 監視対象プロジェクトの `aidlc/` と `.claude/` には一切書き込まない（読み取り専用）。設定ファイルなどもダッシュボード側に置き、各プロジェクトには何も追加しない | 当初要件・要件変更その1・その2 |
| C-2 | サーバーは 127.0.0.1 のみで待ち受け、外部からアクセスできないようにする | 要件変更その1 |
| C-3 | 外部ネットワーク通信をしない。画面で使うスクリプトやフォントも外部（CDN など）から読み込まないと解釈する | 当初要件＋解釈（回答のまとめで確認済み） |
| C-4 | AI-DLC が前提としている bun で動く TypeScript で実装する | 当初要件 |
| C-5 | 壊れたファイルや想定外の形式のファイルがあってもクラッシュせず、警告を出して続ける。1プロジェクトの失敗を他のプロジェクトに波及させない | 当初要件・要件変更その2 |
| C-6 | 状態ファイルなどの実際のフォーマットは推測せず、リポジトリ内の実ファイルとフレームワークのドキュメントで確認する | 当初要件 |

## 7. 受け入れ基準（当初要件から継承）

- 監視対象に Intent が0件でもエラーにならず、「対象なし」と表示される。
- テスト用のデータ（承認待ち・修正中・完了が混ざった複数 Intent）で、一覧が正しく出ることをテストで確認できる。
- 実際のプロジェクトで動かし、表示内容が `/aidlc --status` と食い違わない。

## 8. 技術面の初期リスク（アーキテクト視点・feasibility への引き継ぎ）

解決策はここでは決めず、feasibility で調べる論点として挙げます。

| ID | リスク・論点 | なぜ重要か |
|----|-------------|-----------|
| R-1 | 承認待ちの記録 `[?]` は省略でき、省略されると承認待ちでも「進行中 `[-]`」のままになる | 「取りこぼさない」という中心的な価値に直結する（Q5: D の判断材料）。SM-2 の測定にも影響する |
| R-2 | 127.0.0.1 で待ち受けるだけでは、同じブラウザで開いた悪意あるWebページからの読み取り（DNS リバインディング等）を防げない | ダッシュボードは要件文や設計書の中身を返す可能性がある。C-2 の「外部からアクセスできない」を実質的に満たすための対策の要否を確認する |
| R-3 | 複数リポジトリのファイル変更を同時に監視する方法の信頼性と負荷（監視対象が増えたとき、リポジトリが移動・削除されたとき） | 「数秒以内に反映」と「1プロジェクトの失敗を波及させない」の両立 |
| R-4 | `aidlc-state.md` の `Project` フィールドに、見出し（`## `）を含む複数行の要件文がそのまま入っている | 見出しを手がかりに読み取る素朴な方法では、セクションの境目を誤認するおそれがある |
| R-5 | 監査ログのファイルが、Intent の記録ディレクトリ配下（`<record>/audit/`）と、Space 直下（`intents/audit/`）の両方にある。実ファイルでは、Space 直下には Intent 作成前の出来事（スコープ判定）1件だけが入っていた | 「承認待ちになった日時」を正しく取るには、どちらをどう読むかの確認が必要。Space 直下のログが仕様どおりのものか、Intent 作成前の一時的な書き込みかも確かめる |
| R-6 | フレームワーク（aidlc-workflows v2）の更新で、状態ファイルや監査ログの形式が変わる可能性 | OSS公開（Q6: B）を視野に入れると、形式の変化にどこまで追従するかが問題になる |

## 9. 用語集

| 用語 | 意味 |
|------|------|
| AI-DLC | AIエージェントと人間が段階（ステージ）ごとに成果物を作り、人間の承認を経て進める開発手法。本ダッシュボードが見張る対象 |
| プロジェクト | AI-DLC を使っている1つのリポジトリ（`aidlc/` ディレクトリを持つ） |
| Space | プロジェクト内の作業の区画。多くの場合 `default` の1つだけ |
| Intent | 1つの開発テーマ（作りたいもの・直したいもの）の単位。Space の中に複数ある |
| ステージ | Intent を進める段階（例: 要件分析、設計、コード生成）。各ステージの終わりに承認ゲートがある |
| 承認ゲート | ステージの成果物を開発者が確認し、承認または差し戻しをする関門 |
| `[?]` / `[R]` / `[-]` | 状態ファイル上のステージの状態記号。それぞれ「承認待ち」「修正中」「進行中」 |
| 監査ログ | AI-DLC が出来事（ステージ開始、承認待ち、承認など）を時刻付きで追記していく記録 |
| 滞留時間 | 承認待ちになってから、承認または差し戻しされるまでの時間 |
