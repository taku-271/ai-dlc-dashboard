## 1. MVP のゴール

AI-DLC を複数のプロジェクト・Intent で並行運用する開発者が、**開きっぱなしのブラウザタブ1つで「自分の対応待ち」を取りこぼさず把握できる**状態を、1〜2週間以内に実現します。

成功の判定は intent-statement §3 の指標に従います。

- **SM-1**：ダッシュボードを1回見るだけで全 Intent の状況把握が完了する（`/aidlc --status` との食い違い0件）
- **SM-2**：承認待ちの滞留時間の中央値が導入前より短くなる（測り方は requirements-analysis で確定。ダッシュボードには各行の経過時間を出し、中央値の集計は手作業で行う）

## 2. 範囲の境界

### 範囲内（MVP で作るもの）

| 区分 | 内容 |
|------|------|
| 監視対象の指定 | ダッシュボード側の設定ファイルに、監視するプロジェクトを書く（複数件を書ける書式。最初は1件でもよい） |
| 読み取り | AI-DLC v2 の構成（`aidlc/spaces/...`）の状態ファイル・Intent 一覧・質問ファイル・監査ログを読む。書式の違いに寛容に読み、読めない部分は警告して続ける。1プロジェクトの失敗を他に波及させない |
| 「あなた待ち」の検出 | 承認待ち `[?]`、修正中 `[R]`、回答待ち（質問ファイルの空欄 `[Answer]:`）、入力待ち（Claude が応答を終えて入力を待っている合図。誤表示の対策を含む） |
| 画面 | 「あなた待ち」一覧（全プロジェクト横断・最上部・どのプロジェクト／Space／Intent か分かる・経過時間）、修正中一覧、Intent 一覧（現在ステージ・進捗・最終更新、「プロジェクト → Space → Intent → ステージ」の階層）、「対象なし」と警告の表示、再読み込みボタン |
| 気づかせる仕組み | タブタイトルに承認待ちの件数（全プロジェクトの合計） |
| 最新状態の反映 | ユーザー全体の設定に置いた Claude Code のフックが自動で合図を送り、ダッシュボードはそのプロジェクトのファイルを読み直して、画面をリロードせずに反映する。起動時には全プロジェクトを読む。Claude Code の外の変更は再読み込みボタンで反映する |
| サーバー | 127.0.0.1 だけで待ち受けるローカルの Web サーバー |
| 導入 | フックの登録手順を手順書（README）に書き、利用者が手で登録する |
| 品質 | テスト用データ（承認待ち・修正中・完了が混ざった複数 Intent、壊れたファイルを含む）を使った自動テスト。macOS の実機での動作確認 |

### 範囲外（今回はやらない）

| 項目 | 理由・扱い |
|------|-----------|
| ダッシュボードからの承認操作 | 承認は必ず Claude Code 上で行う（intent-statement のスコープ外） |
| Slack などへの通知、デスクトップ通知、ファビコンのバッジ | タブタイトルの件数で足りるとした（intent-capture Q7） |
| 自動起動・常駐 | 手動で起動し、タブを開いておく運用（intent-capture Q3） |
| ルール数の推移、セッションコストの表示 | MVP 後に検討（当初要件） |
| 監査ログからの「承認待ちの可能性」の推定 | 回答待ち・入力待ちの検出で代える（feasibility Q6） |
| 旧形式（`aidlc-docs/`）の読み取り | v2 の新構成だけを対象とする（feasibility Q3、制約 C-9） |
| 滞留時間の中央値の表示 | 集計は手作業で行う（Q6） |
| フック登録のセットアップコマンド | MVP は手順書で手動登録（Q5） |
| Claude Code プラグインでの配布 | 正式版で対応する（Q5）。ユーザー単位で有効化する前提（制約 C-1・C-7） |
| MCP による連携 | 不採用（feasibility Q9、制約 C-10） |

### 条件付きの項目

| 項目 | 発動条件 | 出典 |
|------|---------|------|
| Host ヘッダー確認（DNS リバインディング対策）と、データ分類・規制の見直し | 仕事や顧客の案件を監視対象に加える**前** | constraint-register の C-11・C-15 |
| Linux・Windows での動作確認 | 期間に余裕があれば MVP 内で行う（Should）。設計は全OS対応を前提とする（制約 C-8 は維持） | Q3 |

## 3. 価値の流れ（バリューストリーム）

承認ゲートが開いてから作業が再開するまでの流れと、ダッシュボードが短くする区間です。

| 段階 | 現状（ダッシュボードなし） | MVP 導入後 | 関係する機能 |
|------|------------------------|-----------|-------------|
| 1. AIエージェントがステージを終え、承認ゲートを開く（または質問を出す） | 状態ファイルに記録される（`[?]` は省略されることがある） | 同じ | — |
| 2. 合図がダッシュボードに届く | — | フックの合図を受けて、数秒以内に画面とタブタイトルが変わる | 変更の合図、読み直し、自動反映 |
| 3. **開発者が気づく** | セッションを順に覗くまで気づかない。ときどき見落とす（intent-capture Q1） | 裏のタブのタイトルの件数で気づく | タブタイトルの件数、「あなた待ち」一覧 |
| 4. 開発者がどこを見ればよいか分かる | Intent ごとに切り替えて確認する | 一覧で、どのプロジェクト／Intent の何を待っているかと経過時間が分かる | 「あなた待ち」一覧、経過時間、階層表示 |
| 5. 開発者が Claude Code で承認・回答する | 同じ | 同じ（ダッシュボードからは承認しない） | — |
| 6. AIエージェントが作業を再開する | 同じ | 同じ | — |

**短くなる区間は 3（気づくまで）と 4（探す手間）** です。成功指標 SM-2（滞留時間）の改善は主にこの2区間から生まれる、という仮説です。

## 4. 進め方の方針

| 項目 | 方針 | 根拠 |
|------|------|------|
| 順序 | 最初に、全体を薄く1本通すウォーキングスケルトンを作り、承認を得てから残りを進める | org.md の Walking Skeleton（新規の mvp） |
| スケルトンで確かめたいこと（デリバリー視点の提案） | 「設定ファイルで1プロジェクトを指定 → 状態ファイルを読む → 承認待ちを画面に出す → フックの合図で読み直して自動反映 → タブタイトルに件数」が端から端までつながること。最大の不確実性である変更の合図（フック）を最初に通す | feasibility RAID の AS-4（ユーザー全体の設定でのフックの動作は未検証） |
| 期間 | 1〜2週間（Must 16件のまま） | Q8-D |
| 確認点 | スケルトン完成時点で実際の進み具合を確かめる（範囲の見直しはしない前提だが、遅れが明らかなら相談する） | Q8-D、RAID RK-7 |

## 5. 期間と範囲の検証

| 項目 | 見積もり |
|------|---------|
| 開発者が使える時間 | 1日30分〜1時間 × 7〜14日 ＝ 約3.5〜14時間（Q7-B） |
| 残り16ステージ（このステージを含む）の質問・レビュー・承認 | 1ステージ20〜30分として約5〜8時間（実装後の動作確認は別） |
| 判定 | 2週間なら収まる見込み。1週間では厳しい。Must の比率が高く余裕は少ない |
| 決定 | ユーザーは推奨（2週間目標＋スケルトン後の見直し）を検討したうえで「このまま進める」を選んだ（Q8-D）。期間超過のリスク（RAID RK-7）は承知のうえで受け入れる |

## 6. intent-statement からの変更点

| intent-statement の箇所 | この文書での扱い | 根拠 |
|------------------------|----------------|------|
| §5「MVPに含めないもの」の回答待ち・可能性の高いものの検出 | 回答待ちと入力待ちは **MVP に含める**（Must）。監査ログからの推定は範囲外 | feasibility Q6、本ステージ Q2 |
| §5 MVP 項目6（ファイル変更の検知） | フックの合図＋読み直し＋起動時の全読込＋再読み込みボタン | feasibility Q8〜Q10、本ステージ Q4 |
| §5 に記載のない項目 | 承認待ちの経過時間（Must）、手順書によるフック登録（Must）を追加 | 本ステージ Q5・Q6 |
| §6 制約 | constraint-register の C-1〜C-16 を正とする | feasibility |
