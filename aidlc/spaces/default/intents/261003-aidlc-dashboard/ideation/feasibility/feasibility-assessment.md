## 1. 結論

**総合判定：実現可能（条件付き）**

MVP の各要求は、技術的に実現できる見込みです。主要な仕組み（ローカル限定の待ち受け、変更を受けた即時の読み直し、AI-DLC ファイルの読み取り）は、このマシンでの試験と実ファイルの確認で裏付けがあります。

条件として次の3点が残ります。いずれも致命的ではなく、後続ステージで対処できます。

1. **「入力待ち」表示（Q6-F）の判定条件**：AI-DLC 自身の仕組みが応答の終了を差し止めることがあるため、単純な判定では誤表示が起きうる（RAID の RK-2）。
2. **Claude Code の外で起きた変更**：別クローンからの取り込みや手作業の編集は、フックの合図では拾えない（RK-3）。
3. **期間（1〜2週間）と範囲の釣り合い**：scope-definition で優先順位を付けて調整する（Q12-D、RK-7）。

## 2. 変更の伝え方の比較と決定

intent-capture の時点では「`aidlc/` 配下のファイル変更を検知する」としていました。Q1 でユーザーから「Claude が都度送ればよいのでは」という提案があり、3つの方式を比較しました。

| 観点 | 方式1：ファイル監視 | 方式2：Claude が MCP で状況を送る | 方式3：Claude Code のフックで合図＋ファイルを読み直す |
|------|-------------------|--------------------------------|----------------------------------------------|
| 送り忘れ・取りこぼし | 起きにくい（OS が通知） | **起きうる**（送るかどうかが Claude の判断次第。R-1 と同種の問題） | 起きにくい（ツールが動くたびに自動で合図） |
| `/aidlc --status` との一致（SM-1） | 一致する（ファイルが正） | **ずれうる**（送られた内容とファイルが別物） | 一致する（合図は読み直しのきっかけで、内容はファイルから読む） |
| OS ごとの違い | **あり**（監視の仕組みがOSごとに違う。macOS は検証済み） | なし | 小さい（フックは Claude Code の仕組み） |
| 各プロジェクトへの追加物 | なし | 指示の置き場所次第（C-1 に抵触しうる） | なし（ユーザー全体の設定に置く。Q10-A） |
| Claude Code の外の変更 | 拾える | 拾えない | **拾えない**（補完策が必要。RK-3） |
| 偽の合図への耐性 | 該当なし | 偽の内容を表示させられる | 害なし（読み直すだけ） |

**決定（Q8・Q9・Q10）：方式3。** ユーザーの提案である「Claude 側から知らせる」発想を、送り忘れが起きない形で実現します。MCP は使いません。
却下した方式1は、OS ごとの違いが全OS対応（Q1-C）の負担になるため不採用としました。ただし、補完策の候補としては残します。方式2は、中心価値である「取りこぼさない」と SM-1 を満たせないため不採用です。

## 3. 領域ごとの実現性

| 領域 | 判定 | 根拠 | 残る課題 |
|------|------|------|---------|
| AI-DLC ファイルの読み取り | 実現可能 | 状態ファイル・Intent 一覧（`intents.json`）・監査ログ・質問ファイルの実物と書式の説明書を確認。状態ファイルは一時ファイルに書いてから置き換える方式で、書きかけを読む心配がない | 監査ログは追記方式のため、追記中に読むと最後の1件が欠けうる（RK-8）。v2 の書式の違いへの寛容さ（Q3-B）の程度は要件で定める |
| 変更の伝達（フック） | 実現可能 | このリポジトリの AI-DLC 自身が、ツール実行後・応答終了時・セッション開始と終了のフックを使い、セッションIDやツール名を受け取っている | 登録方法（誰がユーザー全体の設定に書くか）。他の Claude Code 利用への影響（RK-9） |
| リロード不要の即時反映 | 実現可能 | ローカルのサーバーからブラウザへ更新を届けるのは一般的な仕組みで、特別な前提はない | 「数秒以内」の具体的な秒数は requirements-analysis で決める |
| タブタイトルの件数表示 | 実現可能 | ブラウザの標準機能で足りる | なし |
| 「あなた待ち」の検出（Q6: B + F） | 実現可能（条件付き） | B：空欄の `[Answer]:` は、AI-DLC 自身が人間の回答待ちの目印として使っている。F：応答終了のフックは存在する | F の誤表示対策（RK-2） |
| 複数プロジェクト・複数 Space | 実現可能 | Space と Intent はディレクトリ構成と `intents.json` で列挙できる。1プロジェクトの失敗を他に波及させない作りは設計で担保する | 設定ファイルの置き場所・書式は requirements-analysis で決める |
| 127.0.0.1 限定の待ち受け（Q5-A） | 実現可能 | bun 1.4.2 で 127.0.0.1 だけで待ち受けられることを確認 | DNS リバインディングによる読み取りは残る（RK-6）。仕事の案件を監視対象に加える前に Host ヘッダー確認を追加する（Q11-A）。追加時の有効性は試験で確認済み |
| 全OS対応（Q1-C） | 実現可能（未検証あり） | bun は AI-DLC の前提ランタイムで、macOS・Linux・Windows で動く。方式3はOS固有の監視に頼らない | Linux・Windows は未検証（RK-5）。パスの区切り文字や改行コードの違いへの配慮が必要 |
| 規模（Q2：プロジェクト10件・Intent 100件を目安） | 実現可能 | 1 Intent あたりのファイルは小さく、合図を受けたプロジェクトだけを読み直せば負荷は小さい | 性能目標の数値は requirements-analysis で決める |

### 検証の証拠（このマシン：macOS 26.6.2、bun 1.4.2）

作業用ディレクトリで試験しました。監視対象プロジェクトの `aidlc/` と `.claude/` には書き込んでいません。

| 試験 | 結果 |
|------|------|
| フォルダ配下をまるごと監視する方式でのファイル変更検知 | 書き込みから約20ミリ秒で検知。後から作られたフォルダも検知した。ただし変更の種類はすべて同じ名前（rename）で届いた（方式1は不採用だが、補完策を検討する際の参考情報） |
| 127.0.0.1 での待ち受け | 成功 |
| Host ヘッダー確認による拒否 | 正規のリクエストは 200、宛先名を偽ったリクエストは 403 で拒否できた |

## 4. AWS プラットフォームの観点

- **クラウドは使わない。** ダッシュボードは利用者のPC上だけで動き、外部ネットワーク通信もしない（intent-statement の制約 C-3）。AWS のサービス選定、アカウント、コスト見積りは該当しません。
- **実行環境の前提**：bun（AI-DLC の前提ランタイム）と、一般的なブラウザ。追加の基盤は不要です。
- **運用コスト**：ゼロ（ローカル実行のみ）。

## 5. コンプライアンスの観点

| 観点 | 評価 |
|------|------|
| 規制（PCI DSS・HIPAA・SOC 2・個人情報保護法など） | 現時点では該当なし。個人の開発の状況を、本人のPC内で本人に見せるだけで、個人情報を意図して扱わない |
| データ分類 | 現在は「社内（個人）」相当。将来、仕事や顧客の案件を監視対象に加えた場合は「機密」相当になりうる（Q4-C）。状態ファイルには要件文の全文が入ることがある |
| 見直しの条件 | 仕事の案件を監視対象に加える**前に**、Host ヘッダー確認を追加する（Q11-A）。あわせて、その時点でデータ分類と規制の該当性を見直す |
| データの外部送信 | なし（制約 C-3）。フックの合図も PC 内（127.0.0.1）で完結する |
| OSS 公開時 | 公開するときに、ダッシュボード自身のライセンスと依存物のライセンスを確認する。AI-DLC 本体のコードを流用する場合は、そのライセンスも確認が必要（現時点で流用の予定はない） |

## 6. 既存の代替手段との比較（市場調査の代わりの簡易評価）

市場調査はスキップしたため、外部製品の調査は行っていません（根拠のない市場の主張はしません）。ここでは AI-DLC に付属する手段だけと比べます。

| 手段 | できること | ダッシュボードが埋める隙間 |
|------|-----------|------------------------|
| `/aidlc --status` | 選択中の1つの Intent の状況表示。現在ステージが `[?]` のとき承認待ちと表示 | 全プロジェクト・全 Intent を横断した一覧。`[?]` 以外の「あなた待ち」の検出 |
| ステータスライン | 実行中のセッション内での進捗表示 | セッションの外（裏のタブ）での気づき |
| `/aidlc-replay`・`/aidlc-session-cost` | 1つのワークフローの経緯や集計の表示 | 常時表示・リアルタイム性 |

自作する価値はあると判断します。どの既存手段も、「複数 Intent を横断した常時表示」と「承認待ちに気づかせる仕組み」を持っていないためです。

## 7. intent-statement への影響

feasibility の決定により、intent-statement の内容が次のように変わります。intent-statement 本体は承認済みのため書き換えず、この文書を差分の正とします。requirements-analysis で要件に反映してください。

| intent-statement の箇所 | 変更点 | 根拠 |
|------------------------|--------|------|
| §5 MVP項目6「`aidlc/` 配下のファイル変更を検知し…」 | 実現方法を「ユーザー全体の設定に置いた Claude Code のフックが自動で合図を送り、ダッシュボードはそのプロジェクトのファイルを読み直す」に変更。「数秒以内に、リロードせずに反映」という要求は変えない | Q8・Q9 |
| §5「MVPに含めないもの」の「回答待ち」「可能性が高いもの」の検出 | 「未回答の質問ファイル」の検出（Q6-B）と「入力待ち」の合図（Q6-F）をMVPの候補に格上げする。監査ログからの推定（旧C）は含めない。最終的な採否は scope-definition の優先順位付けで決める | Q6・Q12 |
| §6 制約 | C-7〜C-11 を追加（constraint-register を参照） | Q1・Q3・Q5・Q7・Q10・Q11 |
| §8 技術面の初期リスク R-1〜R-6 | RAID ログに引き継ぎ、評価を更新 | 本ステージの調査 |
