## 1. 技術的な制約

| ID | 制約 | 強さ | 出典 | 影響する範囲 | 確認方法 |
|----|------|------|------|-------------|---------|
| C-1 | 監視対象プロジェクトの `aidlc/` と `.claude/` には一切書き込まない（読み取り専用）。各プロジェクトに設定ファイルなども追加しない | 絶対 | intent-statement C-1 | 全体 | テストで、監視対象ディレクトリに書き込みが発生しないことを確かめる |
| C-2 | サーバーは 127.0.0.1 だけで待ち受け、外部のPCからは接続できない | 絶対 | intent-statement C-2、Q5-A | サーバー | 他のネットワーク上の住所から接続できないことを確かめる |
| C-3 | 外部ネットワーク通信をしない。画面のスクリプトやフォントも外部から読み込まない | 絶対 | intent-statement C-3 | 全体 | 画面が外部の住所を参照していないことを確かめる |
| C-4 | bun で動く TypeScript で実装する | 絶対 | intent-statement C-4 | 全体 | — |
| C-5 | 壊れた・想定外の形式のファイルがあってもクラッシュせず、警告を出して続ける。1プロジェクトの失敗を他に波及させない | 絶対 | intent-statement C-5 | 読み取り・表示 | 壊れたファイルを含むテスト用データで確かめる |
| C-6 | ファイルの形式は推測せず、実ファイルとフレームワークの資料で確認する | 絶対 | intent-statement C-6 | 設計・実装 | 設計書に、確認した実ファイルや資料を記す |

| C-8 | macOS・Linux・Windows のすべてで動く | 絶対（ただし確認方法は scope-definition で調整） | Q1-C | 全体 | 各OSでの確認。実機か自動テストかは scope-definition で決める（Q12-D） |

| C-11 | DNS リバインディング対策（Host ヘッダー確認）は、仕事や顧客の案件を監視対象に加える**前に**追加する | 条件付き（発動条件：機密性のある案件の追加） | Q5-A、Q11-A | サーバー | 見直し条件として運用手順・README に明記する |

| ID | 制約 | 強さ | 出典 | 備考 |

## 4. 制約どうしの関係

| 関係 | 内容 |
|------|------|
| C-1 ⇔ C-7 | フックの登録をユーザー全体の設定に置くことで、C-1（各プロジェクトに何も追加しない）を守る |
| C-8 ⇔ C-10 | OS 固有のファイル監視に頼らないことで、全OS対応の負担を減らす |
| C-8 ⇔ C-13 | 全OSの確認は期間を圧迫しうる。確認方法（実機か自動テストか）は scope-definition で決める |
| C-2 ⇔ C-11 ⇔ C-15 | 127.0.0.1 限定は現時点の判断。機密性のある案件を加えるときに、追加の対策と規制の見直しをまとめて行う |
