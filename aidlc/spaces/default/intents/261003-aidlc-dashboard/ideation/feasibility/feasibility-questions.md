## 質問の前に：調査で分かったこと

intent-statement の技術リスク R-1〜R-6 について、実ファイルと実機で確かめました。質問はこの結果を前提にしています。

| リスク | 調べたこと | 結果 |
|--------|-----------|------|
| R-1 承認待ち `[?]` の記録漏れ | フレームワークの手順書と状態更新ツール | `[?]` の記録は手順上「任意」で、記録されるかは Claude（コンダクター）の運用次第。一方で、フレームワーク自身は「質問ファイルに空欄の `[Answer]:` が残っていること」を**人間の回答待ちの目印**として使っている（セッション終了時のチェック）。`/aidlc --status` も「現在ステージが `[?]` のとき」だけ承認待ちと表示する |
| R-2 外部ページからの読み取り | このマシンの bun 1.4.2 で試験 | 127.0.0.1 だけで待ち受けられることを確認。加えて、リクエストの宛先名（Host ヘッダー）を確かめれば、DNS リバインディングを模したリクエストを拒否（403）できることを確認 |

| R-4 状態ファイルの読み取り | 状態ファイルの実物と `/aidlc --status` の実装 | 状態ファイルは「一時ファイルに書いてから置き換える」方式なので、書きかけを読む心配はない。進捗の総数は、各ステージ行の「— EXECUTE / — SKIP」の印から数えられる |
| R-5 監査ログの置き場所 | 監査ログの実物と書式の説明書 | 監査ログはクローン（作業コピー）ごとに別ファイルになる（`<マシン名>-<クローンID>.md`）。追記方式なので、追記の最中に読むと最後の1件が欠けることがある。Space 直下のログには Intent 作成前の出来事が1件あるだけだった |

## Q6. 「あなた待ち」の範囲 — intent-capture で保留にした判断を、調査結果を踏まえて決めます

intent-capture の Q5 では「まず `[?]` のみ。B/C は調査後に決める」としました。調査では、`[?]` の記録は任意で漏れることがある一方、「質問ファイルの空欄 `[Answer]:`」はフレームワーク自身が回答待ちの目印として使っていると分かりました。

- A. `[?]` のみ（`/aidlc --status` と同じ基準。記録漏れは割り切る）
- B. `[?]` に加え、進行中のステージの質問ファイルに空欄の `[Answer]:` があれば「回答待ち」として表示する
- C. B に加え、監査ログから「承認待ちの可能性が高い」ものを推定し、「要確認」として別枠で表示する
- D. MVPは A。B はMVP後に追加する
- E. ダッシュボードは A のまま。代わりに、各プロジェクトの AI-DLC の運用ルールで「承認ゲートの前に必ず `[?]` を記録する」と決めて、記録漏れそのものを減らす（ダッシュボードの外での対策）
- F. A に加え、Q9 で採用したフックの仕組みで「Claude が応答を終えて入力待ちになった」合図も受け取り、プロジェクトごとに「Claude があなたの入力を待っています」と表示する（ステージ単位ではなくセッション単位の表示。Q9 の回答を受けて追加）
- X. Other (please specify)

## Q8. 変更の伝え方 — ダッシュボードはどうやって最新の状況を知りますか？（Q1 への回答「ファイル変更検知じゃなくて、都度 claude が mcp で送れば良いのでは？」を受けて追加）

- A. ファイルを正とする（ダッシュボードが状態ファイル等を読む）。変更の検知はファイル監視を基本とし、取りこぼし対策と、監視が不安定なOS向けに、数秒ごとの再確認（ポーリング）も併用する
- B. Claude が MCP 経由で状況を送る方式に切り替える（ファイルの監視はしない）
- C. A を基本とし、MVP後に「Claude Code のフック（ユーザー全体の設定に置く）から、入力待ちになった合図を送る」仕組みを、「あなた待ち」検出の強化策として検討する
- D. A と B の併用（ファイルを正としつつ、Claude からの送信も受け付ける）
- X. Other (please specify)

[Answer]: B → 矛盾確認の結果（Q9 = C、Q10 = A）、「Claude 側から知らせる」方式は MCP ではなく、ユーザー全体の設定に置いた Claude Code のフックによる自動の合図とし、ダッシュボードは合図を受けてファイルを読み直す形に確定

## Q9. MCP 送信方式の詳細 — 「取りこぼさない」「/aidlc --status と食い違わない」との両立をどう図りますか？（Q8 = B を受けた矛盾確認）

Q8 の B（Claude が MCP で送る）と、これまでに決めた事項が次のようにぶつかります。

| これまでの決定 | Q8 = B で起きること |
|---|---|
| 中心価値「承認待ちを取りこぼさない」（intent-statement §1） | 送るかどうかが Claude の判断次第になり、送り忘れると承認待ちが表示されない（R-1 と同種の問題） |
| 成功指標 SM-1「`/aidlc --status` と食い違い0件」 | Claude が送った内容と、エンジンが正とするファイルの内容がずれる可能性がある |
| ダッシュボードを開きっぱなしにする運用（intent-capture Q3） | ダッシュボードを止めている間に進んだ状況は、送られてこない |

- A. Claude が判断して状況そのものを送る。送り忘れのリスクは受け入れる。ダッシュボードの起動時だけはファイルを読んで初期状態を作る
- B. Claude が MCP で送るのは「このプロジェクトに変化があった」という**合図だけ**にし、ダッシュボードは合図を受けたらそのプロジェクトのファイルを読み直す（内容のずれを防ぐ）。送り忘れに備えて、数十秒〜数分ごとの再確認も入れる
- C. Claude の判断に任せず、Claude Code のフック（ユーザー全体の設定）で、AI-DLC のツールが動くたびに自動で合図を送る。ダッシュボードは合図を受けてファイルを読み直す（送り忘れが起きない。MCP は使わない）
- D. Q8 を A（ファイル監視＋再確認）に戻す
- X. Other (please specify)

[Answer]: C
